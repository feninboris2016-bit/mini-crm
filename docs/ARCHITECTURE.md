# 🏗️ Архитектура Мини-CRM

Документ описывает архитектуру системы, поток данных, организацию базы данных и работу очереди уведомлений.

---

## 1. Общий обзор архитектуры

Система построена по многослойной модульной архитектуре с чётким разделением ответственности:

```
[Посетитель / Сайт]                  [Администратор CRM]
        │                                     │
        ▼ (POST /api/v1/leads)                ▼ (React SPA)
┌────────────────────────────────────────────────────────┐
│                   EXPRESS BACKEND                      │
│                                                        │
│  ┌────────────────────┐       ┌─────────────────────┐  │
│  │ Public Leads API   │       │ Admin Protected API │  │
│  │ (Rate Limit, HP,   │       │ (JWT, Brute-Force,  │  │
│  │  X-Site-Key)       │       │  Audit Logger)      │  │
│  └─────────┬──────────┘       └──────────┬──────────┘  │
│            │                             │             │
│            ▼                             ▼             │
│  ┌──────────────────────────────────────────────────┐  │
│  │                 SERVICES LAYER                   │  │
│  │  - leadsService.ts       - authService.ts        │  │
│  │  - queueService.ts       - exportService.ts      │  │
│  │  - emailService.ts       - backupService.ts      │  │
│  │  - telegramService.ts                            │  │
│  └──────────────────────────┬───────────────────────┘  │
│                             │                          │
│            ┌────────────────┴───────────────┐          │
│            ▼                                ▼          │
│  ┌────────────────────┐          ┌──────────────────┐  │
│  │ Notification Queue │          │ Repository Layer │  │
│  │ (Worker / Retries) │          │ (SQL / Queries)  │  │
│  └─────────┬──────────┘          └──────────┬───────┘  │
└────────────┼────────────────────────────────┼──────────┘
             │                                │
             ▼                                ▼
     [SMTP]   [Telegram API]         [PostgreSQL / SQLite]
```

## 2. Модель данных

База данных содержит 6 ключевых сущностей:

1. **`users`** — учетные записи администраторов CRM:
   - `id`: первичный ключ (`usr_...`).
   - `email`: уникальный адрес входа.
   - `password_hash`: хеш пароля (`bcrypt`, 12 раундов).
   - `role`: роль пользователя (по умолчанию `admin`).
   - `created_at`: дата создания.

2. **`leads`** — поступившие заявки с сайта:
   - `id`: первичный ключ (`lead_...`).
   - `name`: имя клиента.
   - `phone`: телефон (нормализованный, nullable).
   - `email`: email (nullable).
   - `message`: текст сообщения или перечень товаров.
   - `source_url`: URL страницы, с которой отправлена заявка.
   - `source_name`: название формы или раздела.
   - `status`: статус заявки (`new`, `in_progress`, `won`, `lost`).
   - `notification_state`: агрегированный статус уведомлений (`pending`, `sent`, `partial`, `failed`).
   - `external_idempotency_key`: ключ идемпотентности для предотвращения дублей.
   - `created_at`, `updated_at`: временные метки.

3. **`lead_comments`** — внутренние заметки менеджеров:
   - `id`: первичный ключ (`cmt_...`).
   - `lead_id`: внешний ключ к `leads(id)` с каскадным удалением.
   - `author_id`, `author_name`: автор комментария.
   - `comment`: текст заметки.
   - `created_at`: дата создания.

4. **`notification_jobs`** — задачи очереди уведомлений:
   - `id`: первичный ключ (`job_...`).
   - `lead_id`: внешний ключ к `leads(id)`.
   - `channel`: канал доставки (`email` или `telegram`).
   - `status`: статус задачи (`pending`, `processing`, `sent`, `retry`, `failed`).
   - `attempts`: количество выполненных попыток (0..max_attempts).
   - `max_attempts`: максимум попыток (по умолчанию 5).
   - `next_attempt_at`: время следующей попытки.
   - `last_error`: текст ошибки (маскированный, без секретов).
   - `created_at`, `updated_at`, `sent_at`.

5. **`settings`** — динамические настройки:
   - `key`: имя параметра (PK).
   - `value`: сохраненное значение.
   - `updated_at`: дата обновления.

6. **`audit_log`** — журнал действий безопасности:
   - `id`: первичный ключ (`aud_...`).
   - `user_id`, `user_email`: инициатор действия.
   - `action`: тип действия (`login`, `status_change`, `comment_added`, `export_csv`, `settings_updated`, `backup_created`, `backup_restored`, `lead_received`).
   - `details`: структурированные безопасные детали (без паролей и токенов).
   - `ip_address`: IP адрес инициатора.
   - `created_at`: дата записи.

## 3. Двухканальная очередь уведомлений (Queue Service)

Очередь обеспечивает независимую и надёжную доставку:

1. **Атомарная фиксация (Job Claiming)**:
   Перед обработкой воркер атомарно переводит статус в `processing` с проверкой текущего статуса `pending` или `retry`. Это предотвращает гонки при параллельных воркерах.
2. **Экспоненциальная задержка (Exponential Backoff)**:
   При временных сетевых ошибках или лимитах провайдеров следующая попытка откладывается:
   - Попытка 1: через **1 минуту**
   - Попытка 2: через **5 минут**
   - Попытка 3: через **15 минут**
   - Попытка 4: через **60 минут**
   - Попытка 5: переход в статус `failed` (окончательная ошибка с возможностью ручного перезапуска).
3. **Изоляция каналов**:
   Если отправка Email завершилась ошибкой (например, неверный SMTP логин), отправка в Telegram всё равно выполнится и отметится как `sent`.
4. **Совместимость с Serverless и внешними Cron**:
   Помимо внутреннего воркера, очередь поддерживает вызов через защищённый HTTP-эндпоинт:
   `POST /api/v1/jobs/process-queue` с заголовком `X-Cron-Key: <CRON_SECRET>`. Это позволяет развертывать систему на serverless-платформах (Vercel, Netlify Functions, Render spin-down) и запускать воркер по расписанию через cron-job.org или GitHub Actions.
